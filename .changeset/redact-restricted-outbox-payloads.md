Redact the payload of a restricted outbox row once it is published. The statement of `OutboxRelay` that marks a row sent now also replaces the payload of a restricted row (stored on the restricted stream, or on a subject under the restricted prefix) with its envelope and a marker, `{ id, occurredAt, organizationId, actor, version, "$redacted": true }`: the single-use code or link of an event such as `one-time-code.issued.v1` no longer stays readable in `outbox_events` until the purge of sent rows. The message published on `restricted.<name>` still carries the full payload, and unrestricted rows keep theirs. A publish that fails, a crash or a failed commit leaves the payload in place for the next attempt. `requeueOutboxEvents` skips a redacted row, and a relay that finds one pending marks it sent again with a warning instead of publishing it. The relay also redacts, at its first pass and with every purge, the restricted rows sent whole before the upgrade or by a replica still on an older kit, so the table converges once the rollout is over.

No schema migration: the `outbox_events` schema is unchanged and `OutboxRelay` keeps its constructor (the messaging options it now reads are optional). Every service keeps working as it is. Once a replica runs this version, run `requeueOutboxEvents` from this version only: an older kit would requeue a redacted row and its relay would publish the bare envelope, which the consumer terminates as an invalid payload. A service whose specs read a code or a link from `outbox_events` after the relay ran (identity-service) reads it from the message in `EVENTS_RESTRICTED` instead. A restricted event lost with NATS is no longer restored by a requeue: its owner issues a new code or link.
